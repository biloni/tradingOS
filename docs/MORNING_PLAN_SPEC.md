# Morning Plan Spec

**Status: architecture-only (Revision Prompt R1).** This is the target
spec for the Morning Decision Plan and the dashboard that reads it,
implementing PROJECT_INSTRUCTIONS.md's `MDS-*` requirements (adopted in
Revision Prompt R0) in enough detail to build against. Nothing here is
implemented yet — no scheduler, no plan-assembly service, no dashboard
route exists in the current codebase.

## What "the plan" is

One row, conceptually: a `MorningPlan` artifact for one U.S. trading date,
generated by a scheduled job, immutable once published, versioned if it
needs a correction. It replaces docs/UX_MAP.md's original "Premarket Plan"
page concept — same page, promoted to the default landing page and
formalized against R0's `MDS-*` rules rather than the earlier, less
specific premarket-plan description.

## Refresh schedule

- **Preliminary refresh: 05:45 America/Los_Angeles.** Assembles the plan
  from whatever evidence is available at that time, labeled `PRELIMINARY`
  — visible to the user immediately (an early riser isn't stuck looking at
  yesterday's plan for 25 minutes), but never treated as the plan the
  day's decisions are audited against.
- **Final refresh: 06:10 America/Los_Angeles** (R0's `MDS-2` default,
  twenty minutes before the regular U.S. equity open). This is **the**
  official plan for the day — the one version everything else in the
  product (order proposals, the "Approval Required" section, Cowork
  delivery) is allowed to reference.
- Both times are configurable (a versioned config value, principle 8), not
  hardcoded constants — a user in a different timezone, or who wants more
  lead time, changes a setting, not code.
- Only valid U.S. trading days get a plan (market-calendar-aware, reusing
  whatever market-calendar source the scheduler already needs for job
  timing — no separate vendor).

## Immutability and versioning

- The 05:45 `PRELIMINARY` version and the 06:10 `FINAL` version are two
  distinct, separately-stored artifacts for the same trading date — the
  final does not overwrite the preliminary; both remain retrievable
  (`GET /plans/daily?date=...&version=...`-shaped, extending today's
  `GET /api/v1/plans/daily`).
- Once `FINAL` is published, it is never edited in place. If new evidence
  later contradicts something the final plan said (e.g. a data correction
  arrives at 9am), that does not retroactively change the 06:10 artifact —
  it can only produce a new, later-timestamped correction artifact that
  clearly supersedes the original, the same append-only-version pattern
  `RecommendationVersion` already uses (docs/DATA_DICTIONARY.md).
- A manual "run now" action (already specified in docs/UX_MAP.md's
  Premarket Plan empty state) produces an `AD_HOC` version, never
  silently mistaken for the day's official `FINAL`.

## Reproducibility (architecture question 3)

**How will a morning plan remain reproducible when market data or news
changes later?** By construction, not by re-computation: every fact,
calculation, and inference the plan's `FINAL` version references is a
**stored snapshot as of the plan's evidence cutoff**, not a live pointer
that re-resolves against today's data. Concretely:

- The plan artifact records its own `generated_at` and `evidence_cutoff`
  timestamps (MDS-3).
- Every `RecommendationVersion` it includes is already immutable
  (docs/DATA_DICTIONARY.md, unchanged from Phase 8) — a later recompute
  creates a new version, it never mutates the one the plan already
  pointed to.
- Every evidence item (market bars, news, fundamentals, regime snapshot)
  the plan's committee runs consumed is itself an append-only, timestamped
  row (Phase 8's `market_evidence` bounded context) — re-fetching
  `GET /plans/daily?date=2026-08-05` next month resolves to the exact same
  set of `recommendation_version_id`s and evidence-item ids it did on
  2026-08-05, regardless of what the vendor's API would return for that
  date if queried again today.
- The plan artifact itself stores the **set of ids** it's built from
  (`job_lineage`, below) rather than re-deriving "what was true that
  morning" from a live query — this is the direct mechanism that makes
  NFR-04 ("any past ... scheduled artifact must be fully reconstructable
  from stored data alone") true for this specific artifact, not just an
  aspiration restated.

## Job lineage

A `MorningPlanRun` (new entity, not yet in the schema) records, per
generation:

- `job_run_id` — the `job_runs` row (Phase 8, existing table) that
  triggered this generation.
- `plan_version` — `PRELIMINARY` / `FINAL` / `AD_HOC` / a correction
  sequence number.
- `evidence_cutoff` — the latest timestamp of any evidence item considered
  eligible for this run (never "whatever happened to be fetched most
  recently," an explicit, recorded cutoff).
- `included_recommendation_version_ids` — the exact
  `recommendation_versions` rows surfaced in this plan (both lanes —
  Investment and Tactical, see docs/PRODUCT_REQUIREMENTS.md's R1 delta).
- `regime_snapshot_id` — which `market_regime_snapshots` row this run
  used.
- `data_problems` — a structured list of what was missing/stale/
  unavailable at generation time (feeds the "Data Problems" section
  below), never silently omitted from the record just because it didn't
  block the whole plan.

This is the concrete mechanism behind "reproducible": a `MorningPlanRun`
row is a manifest, and the plan UI is a read-only render of that manifest
plus its referenced (already-immutable) child rows — never a live
recomputation triggered by opening the page.

## What data is required before the plan can be labeled COMPLETE (architecture question 4)

A plan version is `COMPLETE` only if, for every symbol that would
otherwise appear in "Act Now" or "Approval Required":

1. Market data (price/volume) is fresh within its configured staleness
   threshold.
2. The regime classification for the day exists and is not itself stale.
3. Every evidence category a role/gate for that symbol's recommendation
   actually used (technicals always; fundamentals/news/earnings only if
   that symbol's committee run consulted them) is present and fresh —
   **not** every possible evidence category for every symbol regardless
   of relevance; a symbol whose recommendation never needed fundamentals
   isn't blocked by a fundamentals vendor outage.
4. Every deterministic gate relevant to that symbol's recommendation
   (stop/target, position sizing, earnings-window check) actually ran and
   produced a result — a gate that errored, not just one that returned a
   block, prevents `COMPLETE`.

If any symbol fails these checks, that symbol's entry moves to "Data
Problems" (never silently dropped, never silently shown as if complete),
and the **plan as a whole** is labeled `INCOMPLETE` if enough of the
watchlist is affected to materially change what "the day's plan" means —
a threshold percentage of Tier 1 names affected, configurable, defaulting
conservatively (favor labeling `INCOMPLETE` over quietly downgrading a
plan's own honesty about its coverage). A single stale name among 48 does
not incompletestamp the whole plan; a vendor-wide outage affecting most of
the watchlist does. This directly implements R0's `MDS-4` ("publish an
`INCOMPLETE` or `NO_ACTION` plan rather than fabricating certainty").

## Fixed section grouping (R0's MDS-5, restated with content rules)

In this exact order, always:

1. **Act Now** — recommendations whose gates all passed and whose action
   is immediately actionable today (`INVEST_BUY`/`INVEST_ADD`/`TRADE_ENTER`/
   `TRADE_ADD_CONFIRMED` etc. that don't require approval workflow, e.g.
   already covered by an active `PAPER_AUTO_POLICY` grant). Capped at
   **3 actionable new entries** displayed (a new recommended default,
   below) — additional qualifying names still exist in the underlying
   data and are visible via "show more," but the headline count a busy
   user sees at a glance never exceeds 3, matching the persona's "concise"
   requirement (docs/PRODUCT_REQUIREMENTS.md) with an actual number
   instead of a vibe.
2. **Approval Required** — recommendations that passed every gate but
   need an explicit confirmation before anything happens (any
   `PAPER_MANUAL_APPROVAL`/`LIVE_CONFIRM_EACH_ORDER` proposal, and any
   `PAPER_AUTO_POLICY` proposal whose amount/risk exceeds that policy's
   own auto-approval ceiling).
3. **Hold/Manage** — existing open positions (either lane) with a
   `HOLD`/`INVEST_HOLD`/`TRADE_HOLD`/`TRADE_TIGHTEN_STOP`/
   `TRADE_TAKE_PARTIAL` suggestion from the active trade monitor.
4. **Investment Watch** — `INVEST_WATCH` recommendations: names worth
   continued attention on the 3-24 month thesis horizon, not actionable
   today.
5. **Tactical Watch** — `TRADE_WAIT` recommendations: names worth
   continued attention on the 1-10 day horizon, not actionable today.
   Kept structurally separate from Investment Watch even when the same
   symbol appears in both (PM-2's identity-separation rule applies to plan
   display, not just storage).
6. **Avoid** — `INVEST_EXIT`/`TRADE_AVOID`/`TRADE_EXIT` and any name a
   deterministic gate explicitly blocked, shown with the specific gate and
   numbers that blocked it (FR-26, unchanged).
7. **Data Problems** — every symbol/category that failed the `COMPLETE`
   checks above, each with a specific, human-readable reason (never a bare
   "error").

A symbol with both an Investment and a Tactical record (PM-2) may appear
in two different sections at once — e.g. Investment Watch **and** Act Now
(tactical) simultaneously — always as two visually distinct entries, never
merged into one row that would obscure which lane produced which action.

## Cowork read-only delivery (SS-5, ADR-049)

A Cowork scheduled task may read and summarize the `FINAL` plan **only
after it has been published** — never the `PRELIMINARY` version, never a
plan still being assembled. The delivery mechanism is a one-way read: the
Cowork task calls a read-only endpoint (the existing
`GET /api/v1/plans/daily`-shaped contract, extended for plan version), and
has no code path back into order creation, approval, or the execution
service — see docs/ORDER_AUTHORITY_MODEL.md's broker-adapter isolation
section and docs/DECISIONS.md's ADR-049 for the full boundary design.
